# Лабораторная работа 4
## Вариант 28. Тайм-аут и аварийное освобождение Mutex

## 1. Введение
В лабораторной работе рассматривается организация параллельного доступа к общим данным между независимыми процессами в операционной системе Windows. Основная задача — корректно синхронизировать доступ к общей структуре данных с использованием Named Mutex и Shared Memory. Особое внимание уделяется тайм-аутам и аварийному освобождению объекта синхронизации.

## 2. Цель работы
Изучение механизмов взаимного исключения и синхронизации в Windows API, а также практическое моделирование конфликтов при совместном доступе к общему ресурсу.

## 3. Постановка индивидуального задания
Вариант 28:
- три процесса работают с общей структурой данных;
- один процесс удерживает mutex в течение 50 мс;
- остальные процессы пытаются получить доступ с тайм-аутом;
- необходимо обработать WAIT_TIMEOUT и WAIT_ABANDONED;
- при обнаружении несогласованных данных необходимо прекратить использование структуры до восстановления;
- провести эксперименты с тайм-аутами 10 и 100 мс.

## 4. Теоретические сведения
Взаимное исключение необходимо для исключения гонок при совместном доступе к общим данным. В Windows для этого используются объекты синхронизации, в частности Mutex. Если один процесс удерживает mutex, другой процесс блокируется до освобождения ресурса либо до истечения тайм-аута.

Если процесс завершился, не освободив mutex, объект возвращает код WAIT_ABANDONED. Это состояние означает, что доступ к ресурсу был потерян и данные требуют восстановления.

Shared Memory позволяет нескольким процессам обращаться к одному общему участку памяти. Без синхронизации это приводит к некорректным данным и гонкам.

## 5. Архитектура программы
Программа состоит из следующих компонентов:
- parent process — запускает owner и clients;
- owner process — периодически захватывает mutex и пишет в общий блок памяти;
- client process — пытается получить mutex, изменяет данные и освобождает его;
- SharedMemory — класс для доступа к общей памяти;
- Logger — потокобезопасное журналирование;
- ProcessSync — обёртки для mutex и ожидания.

## 6. Описание процессов и общих ресурсов
Общим ресурсом является структура SharedData, размещённая в общей памяти. Каждый процесс работает с одной и той же областью памяти, но доступ к ней регулируется Mutex.

SharedData содержит:
- mutexOwner;
- sequenceNumber;
- valueA, valueB, valueC;
- corruptedFlag;
- lastWriter;
- lastOperationMs;
- lockState;
- version.

## 7. Используемые механизмы синхронизации
Для реализации использованы:
- Shared Memory;
- named Mutex;
- CreateMutexW;
- OpenMutexW;
- WaitForSingleObject;
- ReleaseMutex;
- WaitForSingleObject(timeout);
- InterlockedExchange;
- MapViewOfFile / CreateFileMappingW.

## 8. Алгоритм работы
1. Parent запускает owner process и два client process.
2. Owner циклически захватывает mutex, записывает в память и удерживает ресурс 50 мс.
3. Client-процессы ждут mutex с тайм-аутом.
4. Если тайм-аут истёк, фиксируется WAIT_TIMEOUT.
5. Если owner завершился без освобождения mutex, клиент получает WAIT_ABANDONED и восстанавливает состояние структуры.
6. Проверяется корректность данных, и при нарушении выполняется восстановление памяти.

## 9. Проверяемые инварианты
- один ресурс не может одновременно принадлежать двум процессам;
- данные не должны находиться в повреждённом состоянии;
- mutexOwner должен быть допустимым значением;
- после аварийного завершения owner процесс не должен оставлять ресурс захваченным;
- при обнаружении несогласованных данных выполняется восстановление.

## 10. Методика проведения экспериментов
Эксперименты проводились в двух конфигурациях:
- timeout = 10 ms;
- timeout = 100 ms.

Для каждой конфигурации выполнялось не менее трёх запусков. Данные сохранялись в `data/experiment_results.csv`.

## 12. Анализ результатов
Увеличение тайм-аута снижает частоту срабатывания WAIT_TIMEOUT, поскольку процессы имеют больше времени на ожидание освобождения mutex. При коротком таймауте растёт число отказов, а при длинном таймауте программа стабильнее и больше операций завершается успешно.

Изменение нагрузки не приводит к линейному росту производительности, потому что блокировки и переключение контекста добавляют накладные расходы. На практике критическим фактором является не только загрузка, но и время удержания mutex и вероятность взаимного ожидания.

## 13. Заключение
Использование Mutex и Shared Memory в Windows API позволяет корректно организовать взаимодействие независимых процессов и предотвратить гонки. Обработка WAIT_TIMEOUT и WAIT_ABANDONED обеспечивает отказоустойчивость и корректное восстановление данных после аварийного завершения владельца ресурса.
